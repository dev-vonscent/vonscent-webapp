## F1. Дууссан / зогсоосон арга хэмжээг засахгүй

### Асуудал

Явж буй арга хэмжээг өдрийн дундуур зогсооход `stop_sale_event` нь `ends_at = now()` болгоно (жишээ 14:00).
Дараа нь админ тэр мөрийг нээж (засах товч «Дууссан» дээр ч идэвхтэй) юу ч өөрчлөлгүй, эсвэл нэрийг нь
засаад «Хадгалах» дарвал:

1. Маягт дуусах **өдрийг** илгээнэ: `endsOn = isoEndToDay(ends_at)` = өнөөдөр (`sale-event-admin.tsx:389`).
2. Сервер түүнийг өдрийн төгсгөл болгоно: `endsAt = dayEndIso(endsOn)` = маргаашийн 00:00 (`sale-events/server.ts` `toSaleEventRpc`).
3. `save_sale_event` `ends_at`-ийг дарж бичнэ → арга хэмжээ шөнө дунд хүртэл **дахин LIVE**, үнэ буурна.

Баталгаажуулалт гарахгүй: `save()` доторх «Одоо дэлгүүрт шууд нөлөөлнө» нь зөвхөн `phase === "live"` үед (`sale-event-admin.tsx:488`).

### Шийдвэр

Дууссан (үүнд зогсоосон) арга хэмжээг **засахгүй**. Зөвхөн «Хуулах» үлдэнэ — дахин явуулах бол хуулж шинэ ноорог үүсгэнэ.
Ноорог, товлосон, явж буй арга хэмжээ өмнөх шигээ засагдана.

### Хийх

**DB (0184)** — хамгаалалт клиент дээр биш, санд:

- `save_sale_event` (`create or replace`, гарын үсэг хэвээр): `p_id` өгөгдсөн үед
  одоогийн мөр `is_active and ends_at <= now()` бол `raise exception 'EVENT_ENDED'`.
  Шалгалтыг slug архивлах `update`-ийн **өмнө** хийнэ (эс бөгөөс өөрийнхөө slug-ийг архивлах оролдлого үүснэ —
  одоо `o.id is distinct from v_id` хамгаалж байгаа ч дараалал цэвэр байх ёстой).
  Мөрийг `select … for update`-ээр түгжиж шалгана: зогсоох ба хадгалах зэрэг ирэхэд race гарахгүй.
- Шинэ мөр (`p_id is null`, хуулах) — хөндөгдөхгүй.

**Сервер** — `src/features/sale-events/server.ts` `saleEventWriteError`:

- `/EVENT_ENDED/` → `409`, «Дууссан арга хэмжээг засахгүй. Дахин явуулах бол хуулж шинээр үүсгэнэ үү.»

**Админ UI** — `src/features/sale-events/components/sale-event-admin.tsx`:

- Картын «Засах» (Pencil) товч: `phase === "ended"` үед **харуулахгүй** (`:296` орчим). «Хуулах» хэвээр.
- Нэмэлт хамгаалалт: `EventForm` дууссан мөрөөр `mode: "edit"` нээгдсэн бол (хуучин таб, шууд state) хадгалах товчийг идэвхгүй болгож тайлбар харуулна.
- Дууссан картан дээр жижиг тайлбар: «Дууссан — дахин явуулах бол хуулна уу».

### Тест

- `scripts/test-sale-events.ts`:
  - явж буйг `stop_sale_event` → `save_sale_event(p_id, ижил өгөгдөл)` → `EVENT_ENDED`; `ends_at` өөрчлөгдөөгүй; `variant_price` = үндсэн үнэ хэвээр.
  - хугацаа нь өнгөрсөн (`ends_at` өчигдөр) арга хэмжээ → `EVENT_ENDED`.
  - ноорог, товлосон, явж буй → хадгалагдана (regression).
  - эхлээгүйг зогсоосон (→ ноорог) → засагдана.
  - дууссаныг хуулах (`p_id null`, ижил slug) → OK, хуучны slug архивлагдана (одоогийн тест хэвээр ногоон).
- Vitest: `saleEventWriteError` — `EVENT_ENDED` → 409 + мессеж.
- Гар: зогсоох → карт дээр засах товч алга, «Хуулах» ажиллана.

### Дууссан гэж үзэх

Зогсоосон арга хэмжээ ямар ч замаар (UI, API шууд дуудлага) дахин LIVE болохгүй.

## F2. Эхлээгүй арга хэмжээ рүү заасан hero — анхааруулга

### Асуудал

`live_hero()` (0182): товч нь арга хэмжээ рүү заадаг (`primary_target` / `secondary_target` `type = 'event'`) hero
зөвхөн тэр арга хэмжээ **LIVE** үед л гарна. Тиймээс «11/23-нд эхэлнэ» гэсэн урьдчилсан зарлалын hero-гийн
товчийг Black Friday руу заавал hero дэлгүүрт **огт гарахгүй**, харин админ дээр:

- жагсаалтад «идэвхтэй» гэж харагдана;
- «ирэх 90 хоногийн хуваарь» түүнийг гарна гэж харуулна — `heroSchedule()` товчны арга хэмжээний шалгалтыг
  зориуд алгасдаг (`src/features/heroes/lib.ts:128`, тайлбар: «Товчны арга хэмжээний шалгалтыг энд хийхгүй — тойм»).

Админ яагаад hero гарахгүй байгааг мэдэх аргагүй.

### Шийдвэр

Зан төлөв **хэвээр** (эхлээгүй арга хэмжээ рүү заасан hero гарахгүй) — зөвхөн админд **тодорхой харуулна**.
Урьдчилсан зарлал хийх бол товчийг арга хэмжээ рүү биш, өөр газар (каталог, улирал, дотоод хуудас) заана.

### Хийх

Migration шаардлагагүй. `HeroEventOption`-д `startsAt`, `endsAt`, `isActive` аль хэдийн байгаа.

**`src/features/heroes/lib.ts`**

- Шинэ туслах `heroTargetBlock(h, events, at)`: товчны (primary, secondary) арга хэмжээ `at` мөчид LIVE биш бол
  шалтгааныг буцаана — `{ slug, name, reason: "draft" | "scheduled" | "ended" | "missing", startsAt? }`, эс бөгөөс `null`.
  Дүрэм нь `live_hero()`-ийн `exists (… live_events x where x.slug = …)`-тэй **яг ижил** (нийтлэгдсэн ба `starts_at <= at < ends_at`).
- `heroSchedule()`: өдөр бүрийн нэр дэвшигчийг шүүхдээ `heroTargetBlock(h, events, t) == null`-ийг нэмнэ.
  Дээрх «тойм» тайлбарыг шинэчилнэ. Ингэснээр хуваарь `live_hero()`-тэй таарна.

**`src/features/heroes/components/hero-admin.tsx`**

- Жагсаалтын мөр: hero идэвхтэй, хугацаандаа байгаа ч `heroTargetBlock(now)` буцаавал төлөвийн тэмдгийг
  «Идэвхтэй» биш **«Хүлээгдэж байна»** болгож, доор нь шалтгаан:
  - `scheduled` → «Товчны арга хэмжээ «Black Friday» 11/23-нд эхэлнэ — тэр хүртэл дэлгүүрт гарахгүй.»
  - `draft` → «… нийтлэгдээгүй (ноорог) — дэлгүүрт гарахгүй.»
  - `ended` → «… дууссан — дэлгүүрт гарахгүй.»
- Маягт: товчны холбоос сонгогчид арга хэмжээ сонгох үед, hero-гийн өөрийн хугацаа (эсвэл холбосон арга хэмжээний
  хугацаа) товчны арга хэмжээний хугацаанаас **гадуур** хэсэгтэй бол талбарын доор анхааруулга (хадгалахыг хориглохгүй):
  «Энэ hero зөвхөн «Black Friday» явж байх үед (11/23–11/30) гарна. Урьдчилсан зарлал бол товчийг каталог эсвэл өөр хуудас руу заана уу.»
- Арга хэмжээний сонголтын жагсаалтад төлөвийг нь харуулна (Ноорог / 11/23-нд эхэлнэ / Явж байна / Дууссан).

### Тест

- `src/features/heroes/lib.test.ts`:
  - `heroTargetBlock`: live → null; товлосон → `scheduled` + `startsAt`; ноорог → `draft`; дууссан → `ended`; slug олдохгүй → `missing`; secondary товч ч шалгагдана.
  - `heroSchedule`: 11/20–11/30 хугацаатай, товч нь 11/23-нд эхлэх арга хэмжээ рүү заасан hero → 11/20–11/22-д «Кодын hero» (эсвэл дараагийн hero), 11/23-аас энэ hero.
- `scripts/test-heroes.ts`: `live_hero()` ба TS-ийн дүрэм таарч байгааг нэг тохиолдлоор (товлосон арга хэмжээ рүү заасан hero → хоосон).
- Гар: дээрх hero-г үүсгээд жагсаалт, хуваарь, маягтын анхааруулгыг шалгах.

### Дууссан гэж үзэх

Админ дээр «идэвхтэй» гэж харагдаж байгаа hero бүр дэлгүүрт үнэхээр гарч байгаа; гарахгүй бол шалтгаан нь бичигдсэн. Хуваарь `live_hero()`-тэй таарна.

## F3. Hero-гийн товч арга хэмжээ рүү шууд холбоос

### Асуудал

`heroTargetHref()` арга хэмжээний зорилтыг `/sale/${slug}` болгодог (`src/features/heroes/lib.ts:23`).
`/sale/[slug]` нь зөвхөн `/catalog?event=slug` руу 307 хийдэг route handler тул:

- нүүрний гол товч дээр **илүү нэг хүсэлт** (redirect), Next `<Link>` урьдчилж ачаалж чадахгүй;
- `PromoSlot` popup-ийн давхардлыг хаягийг яг тааруулж шалгадаг (`(shop)/page.tsx:175`, `s.href !== heroHref`) —
  hero `/sale/black-friday`, popup `/catalog?event=black-friday` бол таарахгүй, ижил урамшуулал **хоёр удаа** гарна.

### Хийх

- `heroTargetHref`: `case "event"` → `/catalog?event=${t.slug}`. `/sale/[slug]` route хэвээр үлдэнэ (сошиал пост, сторид өгөх богино хаяг).
- `PromoSlot` дедуп: хоёр хаягийг нэг хэлбэрт оруулж харьцуулна — жижиг `normalizePromoHref(href)`:
  `/sale/x` → `/catalog?event=x`; origin-ийг хасна; каталогийн query-г эрэмбэлнэ. Hero-гийн **хоёр** товчийг (primary, secondary) хоёуланг шалгана.

### Тест

- `lib.test.ts`: event зорилт → `/catalog?event=slug`.
- `normalizePromoHref`: `/sale/x`, `/catalog?event=x`, `https://vonscent.mn/sale/x`, query дараалал өөр — бүгд тэнцүү.
- `hero-resolve.test.ts` / нүүрний тест: hero-той ижил зорилттой popup слайд хасагдана.

## F4. Shop layout-ийн ачаалал

### Асуудал

`src/app/(shop)/layout.tsx` нь `async` болж, `getLiveSaleEvents()`-ийг уншаад `SaleEventsProvider`-д
`badges` (productId → тэмдэг, **бүх** гишүүн бараа) дамжуулдаг. Үр дагавар:

1. Shop-ийн **хуудас бүрийн** RSC ачаалалд арга хэмжээний бүх барааны id орно (FAQ, холбоо барих, блог ч гэсэн).
   200 бараатай Black Friday-д ойролцоогоор 10KB/хуудас — **тооцоо, хэмжээгүй**.
2. `fetchLive` нь `unstable_cache({ revalidate: 60 })`. `src/lib/feature-flags.ts`-ийн тайлбарт бичсэнээр layout-д
   уншсан кэшийн `revalidate` нь тэр layout доорх **бүх хуудсын ISR-ийг** тэр хугацаанд буулгадаг. Одоо shop-ийн
   бүх хуудас 60с тул ялгаагүй, гэхдээ `docs/RELEASE_CHECKLIST.md` §1-ийн «faq, contact, about, blog-ыг 3600 болгох» боломжийг хаана.

### Хийх — эхлээд хэмжинэ

1. dev дээр 200 бараатай туршилтын арга хэмжээ үүсгэж, туг асаалттай / унтраалттай үед `/faq` ба `/catalog`-ийн
   HTML + RSC хэмжээг (gzip) харьцуул. Ялгаа **<3KB gzip** бол (uuid сайн шахагддаггүй тул бодитоор шалгах) засвар хийхгүй, энд үр дүнг тэмдэглээд хаа.
2. Их бол:
   - Layout-аас `badges`-ийг хасаж, зөвхөн chip-д хэрэгтэй `events: {slug, name}[]`-ийг үлдээнэ.
   - Badge-ийг барааны өгөгдөлтэй хамт дамжуулна: `ProductListItem`-д `saleBadge?: string | null` — серверт
     `mapProduct` / `fromCatalogRow`-ийн дараа `eventBadgeMap(live)`-аар бөглөнө (жагсаалт буцаадаг газрууд:
     `getCatalog`, нүүрний rail-ууд, `getRelated`, хүслийн жагсаалт). `SaleBadge` prop-оос уншина, context хэрэггүй болно.
   - Ингэвэл хуудас зөвхөн өөрт харагдаж буй барааны тэмдгийг л зөөнө.
3. ISR: `fetchLive`-ийн `revalidate: 60`-ыг хасаж **зөвхөн tag**-аар шинэчилнэ (`feature-flags.ts`-ийн загвар) —
   админ бичилт `revalidatePublic()`, эхлэх/дуусах мөчийг минут тутмын cron аль хэдийн цэвэрлэдэг.
   `getLiveSaleEvents()` цагаар дахин шүүдэг тул дууссан арга хэмжээ кэшээс гарч ирэхгүй; **эхлэх** мөч нь cron-оос
   хамаарна (≤1 мин) — одоогийнхтой ижил. `fetchPublic`, `fetchLiveHero`-д мөн адил хэрэглэх эсэхийг хамт шийднэ.

### Хэмжилт (2026-11-13)

Layout-ийн `badges` нь HTML-д RSC flight (`self.__next_f.push`, JSON-escape) болж нэг удаа орно.
Тэмдэг «Black Friday», uuid түлхүүр:

| Арга хэмжээний бараа | raw | gzip | brotli |
|---|---|---|---|
| 89 (dev-ийн **бүх** бараа, бодит id) | 5.2KB | 2.0KB | 1.8KB |
| 200 (синтетик uuid) | 11.6KB | 4.3KB | 4.0KB |
| 400 (синтетик uuid) | 23.2KB | 8.7KB | 7.8KB |

Client navigation-д shop layout дахин ирэхгүй тул зардал нь зөвхөн эхний HTML-д.

**Шийдвэр:** одоогийн каталогийн хэмжээнд (бүх бараа орсон ч ≈2KB gzip < 3KB) алхам 2-ыг **хийхгүй**.
Каталог ~150 бараанаас давах эсвэл prod-ийн бодит арга хэмжээ >3KB болвол алхам 2-ыг хийнэ.

Алхам 3 (revalidate хасах) **хийхгүй**: `live_sale_events()` зөвхөн одоо LIVE арга хэмжээг буцаадаг тул
`revalidate: 60`-гүй бол **эхлэх** мөч зөвхөн cron-оос хамаарч, cron алдвал арга хэмжээ дараагийн бичилт
хүртэл гарахгүй. 60с нь тэр үеийн нөөц. Shop хуудсуудыг 3600 болгох үед (RELEASE_CHECKLIST §1) энэ
функцийг товлосныг ч буцаадаг болгож (`getLiveSaleEvents` цагаар шүүдэг) хамт шийднэ.

### Тест

- Хэмжилтийн үр дүн дээр.
- Badge бүх жагсаалтад хэвээр гарч байгааг гар аргаар: каталог, нүүрний rail, төстэй бараа, хайлт, хүслийн жагсаалт.
- Арга хэмжээ эхлэх / дуусахад chip, badge ≤1 минутад солигдоно (cron) — §13.3-ын хуурай гүйлттэй хамт.

## F5. Hero солигдох мөчийн завсар

### Асуудал

`fetchLiveHero` (`src/features/heroes/api.ts`) `live_hero()`-ийн **нэг** мөрийг 60с кэшлэнэ. `getLiveHero()` кэшээс
авсан hero дууссан бол `null` буцааж, нүүр **кодын hero** руу унана — дараагийн DB hero (priority бага боловч
хугацаандаа байгаа) кэш шинэчлэгдэх хүртэл (≤1 мин, cron) гарахгүй. Жишээ: Black Friday-ийн hero 23:59:59-д дуусахад
доор нь байх ёстой «Өвлийн» DB hero-гийн оронд хэсэг хугацаанд кодын hero гарна.

### Хийх

- **0184:** шинэ `live_heroes()` — `live_hero()`-тэй ижил шүүлт, ижил эрэмбэ, гэхдээ `limit 1`-гүй (дээд тал нь 5 мөр).
  `live_hero()`-г хэвээр үлдээнэ (expand only; хуучин код ажиллана). Security definer, `search_path`, grant-ууд ижил.
- `fetchLiveHero` → жагсаалт кэшлэнэ; `getLiveHero()` нь `endsAt > now` бөгөөд `startsAt <= now` **эхний** мөрийг буцаана.
- Эхлэх мөч (шинэ hero кэшэд хараахан ороогүй) нь cron-оос хамаарсан хэвээр — энэ засварын хүрээнд биш.
